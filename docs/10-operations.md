# 10. 운영·회고

### 1. 정기 점검

| 주기 | 점검 내용 | 확인 위치 |
|---|---|---|
| 매일 | Slack 알림 확인, 전날 백업 성공 여부 | Slack `#alarm-cookit`, Grafana |
| 매주 | 서버 자원 추이(CPU·메모리·디스크), 에러 로그, 응답 시간, Gemini 사용량 | Grafana, Loki, Google AI Studio |
| 매월 | OS 보안 업데이트, 인증서 남은 기간, Ansible 설정과 서버 상태 일치 여부(`--check`) | 모니터링 서버(Ansible), Grafana |
| 분기 | 백업 복구 테스트 (09 > 6. 백업·복구 방법과 동일), 비밀 정보 교체 검토 | 모니터링 서버 (임시 컨테이너) |

### 2. 장애 대응 공통 절차

1. 알림 확인: Slack 메시지로 장애 종류·서버 확인
2. 영향 범위 확인: Grafana에서 서비스 접속·에러율·서버 상태 확인
3. 원인 확인: Loki에서 에러 로그 검색, 요청 ID로 LB → WAS 구간 추적
4. 조치: 아래 3. 알림별 대응 기준으로 조치
5. 복구 확인: `[장애 복구]` 알림, Grafana 정상 확인
6. 장애 기록: 5. 장애 기록 양식으로 작성 (`docs/incidents/`, 첫 장애 기록 시 폴더 생성)

### 3. 알림별 대응

| 알림 | 먼저 확인할 것 | 조치 |
|---|---|---|
| **서비스** |  |  |
| 서비스 접속 실패 | LB·WAS 상태, 방화벽 NAT, 도메인 DNS, 인증서 만료(2단계부터) | 멈춘 구간 재시작, 3단계는 VIP 위치 확인 |
| 5xx 에러 증가 | 에러 로그, 최근 배포 여부 | 배포 직후면 `rollback.yml`로 되돌리기 |
| 응답 지연 | 느린 쿼리 로그, DB 연결 수, WAS CPU·메모리 | 원인 쿼리 개선·인덱스 추가, 필요 시 WAS 재시작 |
| Gemini 호출 실패 증가 | Gemini 상태, API 키·사용량 한도 | 외부 장애면 대기 (캐시된 추천은 정상), 한도 초과면 사용량 확인 |
| **서버 자원** |  |  |
| 서버 다운 | 하이퍼바이저에서 VM 상태 | VM 시작, 서비스 자동 시작 확인 |
| 디스크 부족 | 큰 파일 위치 (로그, Docker 이미지, 백업) | 오래된 이미지·로그 정리, 정리 주기 조정 |
| CPU·메모리 과부하 | 원인 프로세스, 요청량 변화 | 원인 프로세스 조치, 지속되면 사양 조정 검토 |
| **구성 요소** |  |  |
| WAS 앱 이상 | 컨테이너 상태, 앱 로그, DB 연결 | 컨테이너 재시작, 배포 직후면 되돌리기 |
| DB 다운 | MariaDB 로그, 디스크 | DB 재시작, 3단계는 DB2 전환 상태 확인 후 DB1 복구 |
| Redis 다운·메모리 | 컨테이너 상태, 메모리 사용량 | Redis 재시작 (서비스는 Redis 없이 유지됨) |
| **운영·이중화** |  |  |
| 모니터링 서버 응답 없음 | 하이퍼바이저에서 VM 상태, Prometheus·Alertmanager 컨테이너 | VM·컨테이너 시작, 그사이 놓친 장애는 서비스 직접 접속으로 확인 |
| 백업 실패·누락 | 백업 로그, 백업 경로 디스크 | 원인 조치 후 수동 백업 1회 실행 |
| 인증서 만료 임박 | certbot 갱신 로그, 3단계는 LB2 동기화 상태 | 수동 갱신(`certbot renew`), 동기화 playbook 실행 |
| LB·DB 전환 발생 | LB1·DB1 상태 | 원인 서버 복구, 자동 복귀 확인 |
| Galera 노드 감소 | DB2·garbd(모니터링 서버) 상태 | 멈춘 노드 시작, 클러스터 노드 수 3 복구 확인 |

※ 알림 조건·등급은 04 상세 설계 > 11. 알림 규칙 기준

### 4. 정기 작업

| 작업 | 방법 | 적용 |
|---|---|---|
| OS 보안 업데이트 | Ansible로 한 대씩 업데이트·재시작 (1·2단계는 서비스 잠시 중단 허용) | 1단계 |
|  | 순서: 대기 서버 먼저 (LB2 → LB1, WAS 한 대씩, DB2 → DB1), 한 대 정상 확인 후 다음 진행. 모니터링 서버 재시작 중에는 알림·배포 중단 (생존 신호 알림은 미리 일시 정지) | 3단계 |
| 비밀 정보 교체 | GitHub Secrets·Vault 값 변경 후 재배포. JWT 키 교체 시 전체 사용자 재로그인 | 1단계 |
|  | DB·Redis 비밀번호: Ansible로 서버 쪽 변경 직후 Secrets 변경·재배포 (사이 시간 API 오류 가능, 사용자가 적은 시간에 진행) | 1단계 |
| 버전 업데이트 | Spring Boot 패치 버전, MariaDB 11.4 패치 버전, 모니터링 도구 (로컬·CI 테스트 후 적용) | 1단계 |
| 전체 재시작 | 호스트 서버 점검 등으로 VM 전체를 끄고 켤 때 시작 순서: 모니터링 → DB → WAS → LB | 1단계 |
|  | Galera는 마지막까지 살아 있던 DB부터 클러스터를 새로 시작, 나머지 DB는 그다음 합류 (04 > 8. MariaDB, 데이터 유실 방지) | 3단계 |
