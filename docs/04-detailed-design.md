# 04. 상세 설계

## 인프라 설계

### 1. 서버 사양

| 단계 | 호스트명 | IP (끝자리 계획) | 역할 | vCPU | 메모리 | 디스크 |
|---|---|---|---|---|---|---|
| 1 | cookit-lb01 | .101 | Nginx (LB) | 2 | 4GB | 200GB |
| 1 | cookit-was01 | .111 | Spring Boot, HAProxy | 2 | 4GB | 200GB |
| 1 | cookit-db01 | .131 | MariaDB | 2 | 4GB | 200GB |
| 1 | cookit-mon01 | .121 | 모니터링, Redis, Runner | 2 | 8GB | 200GB |
| 3 | cookit-lb02 | .102 | Nginx (LB) | 2 | 4GB | 200GB |
| 3 | cookit-was02 | .112 | Spring Boot, HAProxy | 2 | 4GB | 200GB |
| 3 | cookit-db02 | .132 | MariaDB | 2 | 4GB | 200GB |
| 합계 | 1단계 4대 → 3단계 7대 |  |  | 8 → 14 | 20 → 32GB | 800GB → 1.4TB |

**비고**

1. IP 대역은 할당 후 확정, 끝자리는 역할별 10단위 (LB 10x, WAS 11x, 모니터링 12x, DB 13x)
2. 전체 공통: node_exporter, Grafana Alloy, chrony, firewalld
3. 단계별 추가: 2단계 certbot(LB), 3단계 keepalived(LB)·Galera(DB)·garbd(모니터링)
4. VM 템플릿 1개(2코어 4GB, 200GB)로 복제, 모니터링 서버만 메모리 8GB로 상향. 호스트 여유 용량과 씬 프로비저닝 가능 여부 확인 필요
5. 자세한 구성은 03 기술 스택 참고

### 2. 네트워크·DNS

| 항목 | 1단계 | 2단계 | 3단계 |
|---|---|---|---|
| 내부 서버망 | 전체 서버 동일 대역 1개 (대역은 할당 후 확정) |  |  |
| 가비아 A 레코드 | `cookit.neurondev.co.kr` → 공인 IP (단계 간 변경 없음) |  |  |
| 방화벽 NAT | 공인 IP:80 → LB1:80 | 공인 IP:80·443 → LB1 | 공인 IP:80·443 → VIP |
| VIP | - | - | 끝자리 `.100` (keepalived) |
| 접속 주소 | http:// | `https://` (80은 443으로 리다이렉트) |  |

**비고**

1. 공인 IP는 보안상 문서에 기재하지 않음
2. 내부망 PC에서 도메인 접속 시 NAT 헤어핀 지원 여부 확인 필요, 미지원 시 내부 DNS 또는 hosts 파일로 우회
3. 서버 간 통신은 도메인 대신 내부 IP 사용 (Ansible inventory로 관리)

| 외부 사용자 | LB (NAT 경유) | 443 | HTTPS 서비스 접속 | 2단계 |
| **서버 간 (서비스)** |  |  |  |  |
| LB | WAS | 8080 | API 전달 | 1단계 |

| **서버 간 (운영)** |  |  |  |  |
| 모니터링 | 전체 | 9100 | 서버 지표 (node_exporter) | 1단계 |
| 모니터링 | LB | 9113 | Nginx 지표 | 1단계 |
| 모니터링 | WAS | 8080, 8404 | 앱 지표 (Actuator), HAProxy 지표 | 1단계 |
| 모니터링 | DB | 9104 | DB 지표 (mysqld_exporter, MariaDB 지표 수집) | 1단계 |
| 전체 | 모니터링 | 3100 | 로그 전송 (Alloy → Loki) | 1단계 |
| 모니터링 (Ansible·Runner) | 전체 | 22 | 서버 구성 실행, 배포 명령 실행 | 1단계 |
| DB | 모니터링 | 22 | 백업 파일 전송 (rsync) | 1단계 |
| **관리자 (내부망에서만)** |  |  |  |  |

| 전체 | 외부 | 53, 123 (UDP) | DNS 조회, 시간 동기화(NTP) | 1단계 |
| WAS | 외부 | 443 | Gemini API, GHCR 이미지 받기 | 1단계 |
| 모니터링 | 외부 | 443 | GitHub, Slack, healthchecks.io | 1단계 |
| LB | 외부 | 443 | Let's Encrypt 인증서 발급 | 2단계 |

**비고**

1. 기본 정책은 모두 차단, 표에 있는 연결만 허용
2. 외부에 열리는 포트는 LB의 80·443뿐, 관리용 포트(22, 3000)는 내부망에서만 접근
3. 적용 열은 해당 단계부터 적용 (예: 2단계 → 2·3단계 적용)

## 구성 요소 설계

### 5. Nginx (LB)

| 구분 | 설정 | 적용 |
|---|---|---|
| 화면 | React 빌드 파일 서빙, 없는 경로는 `index.html`로 응답 (SPA) | 1단계 |
|  | 빌드 파일(js·css)은 1년 캐시, `index.html`은 캐시 안 함 (배포 즉시 반영), gzip 압축 | 1단계 |
| API 분배 | `/api` → upstream(WAS 목록), 라운드로빈 | 1단계 (3단계 WAS2 추가) |
|  | 장애 WAS 제외: 10초 안에 2회 실패 시 10초간 제외 (`max_fails=2 fail_timeout=10s`) | 3단계 |
|  | 연결 실패 시 다른 WAS로 재시도, 이미 전달된 POST 요청은 재시도 안 함 (중복 추천 방지) | 3단계 |
| 타임아웃 | API 응답 대기 40초 (Gemini 30초 + 여유) | 1단계 |
|  | WAS 연결 시도 2초 (`proxy_connect_timeout`), 꺼진 WAS를 빨리 포기하고 다른 WAS로 재시도 | 3단계 |
| 헤더 전달 | `X-Forwarded-For`·`X-Real-IP`: 사용자 실제 IP (IP별 요청 제한용) | 1단계 |
|  | `X-Forwarded-Proto`: 원래 요청이 HTTPS인지 전달 | 2단계 |
|  | `X-Request-ID`: 요청마다 ID 생성, 로그 추적용 | 1단계 |
| 보안 | 버전 정보 숨김, 기본 보안 헤더 (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`) | 1단계 |
|  | 요청 본문 크기 1MB 제한 | 1단계 |
|  | `/api` 과도한 요청 차단: IP당 초당 10회 (`limit_req`), 차단 시 429 응답 (기본값 503은 서버 오류로 보여 5xx 알림 오발생) | 1단계 |
| HTTPS | 443 설정, TLS 1.2·1.3만 허용, HTTP/2 사용 | 2단계 |
|  | 80 → 443 리다이렉트 (`/.well-known/acme-challenge` 제외) | 2단계 |
|  | HSTS(브라우저가 항상 HTTPS로 접속) 적용, 안정화 확인 후 | 2단계 |
| 로그·지표 | 접속 로그 JSON 형식 (요청 ID, 처리 WAS, 응답 시간 포함) → Alloy가 Loki로 전송 | 1단계 |
|  | 상태 페이지(`stub_status`)는 서버 내부에서만 열고 nginx_exporter가 수집 | 1단계 |
| 이중화 | LB1·LB2 설정 동일 (Ansible로 배포), LB2는 인증서 갱신 확인 요청을 LB1로 전달 | 3단계 |
|  | 인증서 동기화: 모니터링 서버에서 매일 playbook 자동 실행(예약 작업), LB1 인증서가 바뀌었으면 LB2에 복사 후 Nginx 재적용 | 3단계 |

**비고**

1. 초당 요청 차단(Nginx)은 공격성 요청 방어용, 하루 추천 횟수 제한(FR-09)은 앱이 Redis로 처리
2. IP별 제한을 위해 방화벽 NAT가 사용자 원래 IP를 유지하는지 확인 필요 (주소 변환 시 모든 요청이 같은 IP로 보임)

### 6. HAProxy (WAS 내부)

| 구분 | 설정 | 적용 |
|---|---|---|
| 실행 위치 | 각 WAS 서버에서 Docker 컨테이너로 실행, Spring Boot와 같은 서버 | 1단계 |
|  | 앱은 같은 서버의 HAProxy(3306)로만 접속, DB 주소를 앱이 직접 알지 않음 | 1단계 |
| 동작 방식 | TCP 모드 (DB 통신 내용은 그대로 전달) | 1단계 |
| DB 등록 | DB1만 등록 | 1단계 |
|  | DB1 기본, DB2는 `backup` (DB1 장애 시에만 사용) | 3단계 |
| 상태 확인 | 2초마다 확인, 3회 연속 실패 시 제외·2회 연속 성공 시 복귀 | 1단계 |
|  | Galera 동기화 완료 상태인지 확인하는 스크립트(9200) 기준 (동기화 중인 DB로는 연결 안 함) | 3단계 |
| 전환 동작 | DB1 제외 시 DB1과 맺고 있던 연결을 끊어 앱이 바로 DB2로 재접속 | 3단계 |
|  | DB1 복구·동기화 완료 후 자동 복귀, DB2 쪽 연결 정리 | 3단계 |
| 타임아웃 | 연결 시도 3초, 유휴 연결은 앱 커넥션 풀 유지 시간보다 길게 (예: 30분) | 1단계 |
| 로그·지표 | 상태 페이지(8404)에서 Prometheus 형식 지표 제공, 로그는 컨테이너 로그로 Alloy가 수집 | 1단계 |

**비고**

1. 앱(Spring Boot) 커넥션 풀은 연결 검사 후 사용하도록 설정해, 전환 시 끊어진 연결을 바로 교체
2. 1단계부터 HAProxy를 거치게 해 3단계에서 앱 설정 변경 없이 DB2만 추가

### 7. Redis

**키 설계**

| 용도 | 키 | 형식 | 만료 | 동작 |
|---|---|---|---|---|
| 추천 캐시 | `cookit:recipe:cache:{입력 해시}` | String (추천 결과 JSON) | 3일 | 재료(정렬·공백 제거)·식단 모드·추천 개수가 같으면 같은 키 |
| 요청 제한 | `cookit:ratelimit:guest:{IP}:{날짜}`<br>`cookit:ratelimit:user:{회원ID}:{날짜}` | String (횟수) | 당일 자정 | 요청마다 1 증가, 비회원 5회·회원 30회 초과 시 거절 |
| 계정 찾기 제한 | `cookit:ratelimit:account:{IP}:{날짜}` | String (횟수) | 당일 자정 | 아이디 찾기·비밀번호 재설정 요청마다 1 증가, 5회 초과 시 거절 |
| 인기 랭킹 | `cookit:ranking:recipe` | Sorted Set (레시피별 점수) | 없음 | 추천 +1, 즐겨찾기 +3 (해제 시 -3), 상위 5개 조회 |

**설정**

| 구분 | 설정 | 적용 |
|---|---|---|
| 실행 위치 | 모니터링 서버에서 Docker 컨테이너로 실행, 포트 6379 | 1단계 |
| 접근 제한 | 비밀번호 인증, 방화벽으로 WAS에서만 접속 허용 | 1단계 |
| 메모리 | 최대 512MB, 가득 차면 만료 시간이 있는 키(캐시·요청 제한)부터 삭제 → 랭킹은 유지 (`volatile-lru`) | 1단계 |
| 디스크 저장 | AOF(변경 기록) 1초마다 저장, Redis 재기동 후에도 캐시·요청 횟수·랭킹 유지. AOF 파일은 서버 디스크(Docker 볼륨)에 저장 | 1단계 |
| 앱 연결 | 연결·응답 타임아웃 1초, 실패 시 Redis 없이 처리 (02 장애 대응 기준) | 1단계 |
| 지표 | redis_exporter로 메모리 사용량, 캐시 적중률, 연결 수 수집 | 1단계 |

**비고**

1. 키 앞에 `cookit:`을 붙여 서비스별 구분
2. 날짜·자정 기준은 Asia/Seoul
3. 랭킹은 레시피 이름 기준으로 집계 (07 애플리케이션 개발 > 4. 핵심 구현 설계)
4. Redis 데이터는 별도 백업 안 함 (캐시·요청 횟수는 사라져도 무방, 랭킹은 AOF로 유지)

### 8. MariaDB

| 구분 | 설정 | 적용 |
|---|---|---|
| 설치 | DB 서버(VM)에 직접 설치, MariaDB 11.4 LTS 공식 저장소 사용 | 1단계 |
| 기본 설정 | 문자셋 `utf8mb4` (이모지 포함 저장), 시간대 Asia/Seoul | 1단계 |
|  | 저장 엔진 InnoDB만 사용, 모든 테이블에 기본 키(PK) 필수 (Galera 복제 조건) | 1단계 |
| 메모리 | 데이터 캐시(`innodb_buffer_pool_size`) 2GB (서버 메모리 4GB의 절반, 부하 테스트 후 조정) | 1단계 |
| 연결 | 최대 연결 200개 (WAS당 커넥션 풀 10개 기준 여유 확보, 부하 테스트 후 조정) | 1단계 |
|  | 내부 IP로만 접속 허용, 방화벽으로 WAS·모니터링 서버만 허용 | 1단계 |
| 로그 | 느린 쿼리 로그 (1초 이상), 에러 로그 → Alloy가 Loki로 전송 | 1단계 |
| Galera | 클러스터 구성: DB1·DB2·garbd, 복제 형식 `binlog_format=ROW`, `innodb_autoinc_lock_mode=2` | 3단계 |
|  | 새 노드 전체 복사(SST)는 mariabackup 방식 (복사 중에도 DB1 서비스 유지) | 3단계 |
|  | 변경 기록 보관(`gcache`) 1GB, 잠시 끊겼다 돌아오면 차이만 복제(IST) | 3단계 |
|  | 전체 정지 후 재시작 시 마지막까지 살아 있던 노드부터 시작 (데이터 유실 방지) | 3단계 |

## 운영 설계

### 9. 백업·복구

| 구분 | 설정 | 적용 |
|---|---|---|
| 목표 | 데이터 유실 최대 24시간 (RPO), 복구 1시간 이내 (RTO) | 1단계 |
| 도구 | mariabackup 전체 백업, 서비스 중단 없이 실행 | 1단계 |
| 주기 | 매일 03:00, systemd timer (Ansible로 설치) | 1단계 |
| 대상 | DB1 | 1·2단계 |
|  | DB2 (대기 DB, 운영 DB 부하 방지) | 3단계 |
| 절차 | 백업 → 압축 → 모니터링 서버 `/backup/db/날짜/`로 전송 (rsync) → DB 서버의 임시 파일 삭제 | 1단계 |
| 보관 | 모니터링 서버에 7일, 이후 자동 삭제 | 1단계 |
| 감시 | 성공 시 완료 시각을 지표로 기록, 실패하거나 26시간 이상 지나면 알림 (warning) | 1단계 |
| 복구 절차 | 백업 파일 복사 → 복원 준비(prepare) → 데이터 디렉터리로 복원 → 권한 정리 → DB 시작 | 1단계 |
|  | 3단계: DB1 복원 후 Galera 클러스터 새로 시작, DB2는 전체 복사(SST)로 다시 합류 | 3단계 |
| 복구 테스트 | 단계별 1회 이상, 모니터링 서버에 임시 MariaDB 컨테이너를 띄워 복원 후 데이터 건수 확인, 걸린 시간 기록 | 1단계 |

**비고**

1. Galera 복제는 백업이 아님 (실수로 지운 데이터도 DB2에 그대로 복제되므로 별도 백업 필요)
2. 백업이 같은 호스트 서버 안(모니터링 서버)에 있어 호스트 장애 시 함께 유실 가능 (한계, 외부 보관은 이후 단계)

### 10. 로그

**수집 대상**

| 서버 | 로그 |
|---|---|
| LB | Nginx 접속 로그(JSON)·에러 로그 |
| WAS | 앱 로그(JSON), HAProxy 로그 (컨테이너 표준 출력) |
| DB | MariaDB 에러 로그·느린 쿼리 로그 |
| 모니터링 | Prometheus·Grafana·Loki·Redis 등 컨테이너 로그 |
| 전체 | 시스템 로그 (journald, SSH 접속 기록 포함) |

**설정**

| 구분 | 설정 | 적용 |
|---|---|---|
| 수집 | 각 서버의 Grafana Alloy가 로그를 읽어 모니터링 서버 Loki(3100)로 전송 | 1단계 |
| 분류 라벨 | 서버명, 서비스(nginx·app·haproxy·mariadb·system), 로그 레벨 (요청 ID는 라벨이 아닌 본문 검색) | 1단계 |
| 요청 추적 | Nginx가 요청마다 ID 생성 → `X-Request-ID`로 WAS 전달 → 앱 로그에 같은 ID 기록 → 응답 헤더로도 반환 | 1단계 |
| 앱 로그 형식 | JSON (시간, 레벨, 요청 ID, 서버명, 클래스, 메시지), 운영은 INFO 이상 | 1단계 |
| 민감 정보 | 비밀번호·토큰·API 키는 로그에 남기지 않음 (마스킹) | 1단계 |
| 보관 | Loki 14일, 서버 로컬 로그는 7일 후 정리 (logrotate, Docker 로그 크기 제한) | 1단계 |
| 조회 | Grafana에서 서버·서비스·레벨·요청 ID로 검색 | 1단계 |

※ 요청 ID를 응답 헤더로도 돌려줘서, 사용자 오류 문의 시 해당 요청의 LB → WAS 로그를 한 번에 조회

### 12. 배포

| 구분 | 설정 | 적용 |
|---|---|---|
| 전체 흐름 | main 반영 → 테스트·빌드(GitHub 서버) → Docker 이미지 GHCR 저장 → Self-hosted Runner(모니터링 서버)가 내부 서버에 배포 | 1단계 |
| 이미지 태그 | Git 커밋 해시 (`latest` 미사용, 어떤 버전이 떠 있는지 명확, 이전 버전으로 즉시 되돌리기 가능) | 1단계 |
| 비밀 정보 | GitHub Secrets 값을 배포 시 WAS 컨테이너 환경 변수로 주입 | 1단계 |
| 백엔드 | WAS1 컨테이너 교체 (교체 중 API 중단 허용) | 1·2단계 |
|  | 롤링: WAS1 교체 → 헬스체크 정상 확인 → WAS2 교체 | 3단계 |
|  | 무중단 조건: 앱은 처리 중 요청을 끝낸 뒤 종료(graceful shutdown), Nginx는 연결 실패 요청을 다른 WAS로 재시도 | 3단계 |
| 프론트 | React 빌드 파일을 LB에 새 폴더로 올린 뒤 연결 경로만 교체 (교체 순간 중단 없음) | 1단계 |
|  | LB1·LB2 모두 업로드 성공 시에만 두 대 함께 교체 | 3단계 |
| DB 변경 | 앱 시작 시 스키마 변경 자동 적용 (Flyway), 롤링 중 구버전 앱도 동작하도록 컬럼 추가 위주로 변경 | 1단계 |
| 실패 처리 | 헬스체크 실패 시 이전 이미지로 자동 되돌림, 다음 WAS 진행 중단 | 1단계 |
|  | WAS2 실패 시 WAS1도 이전 버전으로 되돌림 (WAS 간 버전 일치) | 3단계 |
|  | 수동 되돌리기: 이전 커밋 해시를 지정해 다시 배포 | 1단계 |
| 결과 알림 | 배포·되돌리기 성공·실패를 Slack으로 알림 | 1단계 |

※ 워크플로 파일 등 상세 구성은 08 CI/CD에서 작성
