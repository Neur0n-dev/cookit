# 09. 테스트

### 1. 테스트 구성

| 구분 | 내용 | 도구 | 적용 |
|---|---|---|---|
| 기능 테스트 | FR-01~14 시나리오 점검, 단위·통합 테스트는 CI에서 자동 실행 (07 연계) | 브라우저, JUnit | 1단계 |
| 부하 테스트 | 동시 사용자 50명 기준 응답 시간 측정, 단계별 비교 | k6 | 1·2·3단계 |
| 장애 테스트 | 서버·구성 요소를 하나씩 중지해 서비스 영향·중단 시간 측정, 1단계와 3단계 비교 | blackbox_exporter, k6 | 1·3단계 |
| 배포 테스트 | 배포 중 서비스 영향, 실패 시 자동 되돌림 확인 | k6, GitHub Actions | 1·3단계 |
| 백업·복구·재구축 | 백업 파일로 DB 복구, 초기화한 VM에 Ansible로 재구축 | mariabackup, Ansible | 1·3단계 |
| 알림·HTTPS 테스트 | 장애·인증서 만료·백업 실패 알림 수신 확인, HTTPS 접속·인증서 갱신 확인 | Alertmanager, Slack, curl | 1·2단계 |

**비고**

1. 단계별 목표 수치는 00 기획 > 완료 기준 참고
2. 테스트 시점: 각 단계 구축 완료 직후 해당 단계 테스트 진행
3. 진행 순서: 기능 → 부하 → 장애 → 배포 → 백업·복구 → 재구축 (재구축은 서비스 전체를 초기화하므로 마지막)

### 2. 공통 준비·측정 방법

| 구분 | 설정 |
|---|---|
| 중단 시간 측정 | blackbox_exporter가 서비스 도메인을 1초 간격·타임아웃 1초로 확인 (테스트 중에만, 평시 15초), 접속 실패 구간 = 중단 시간 |
| 접속 확인 경로 | NAT 헤어핀(내부에서 도메인 접속)이 안 되면 LB(3단계는 VIP) 내부 주소로 확인, 도메인은 요청 헤더(Host)로 지정 |
| 테스트 중 트래픽 | 장애·배포 테스트 중 k6로 초당 10요청 지속 호출 (실제 사용 상황 재현, 실패 건수 집계) |
| k6 실행 위치 | 관리자 PC (모니터링 서버에서 실행하면 같은 호스트 자원을 써서 결과 왜곡) |
| 테스트용 설정 | 부하 테스트 중에만 Gemini mock 사용, 추천 횟수 제한 해제 (환경 변수로 전환, 테스트 후 원래 값으로 재배포, 07 > 5. 인프라 연동 구현 규칙) |
| 요청 차단 예외 | Nginx 초당 요청 제한(IP당 10회)에서 관리자 PC IP 예외 (테스트 중에만, Ansible 변수로 전환), 한 IP에서 50명분 요청을 보내므로 필요 |
| 테스트 데이터 | k6용 테스트 계정 50개(`loadtest-` 접두어), mock 레시피 이름은 `[테스트]` 접두어. 테스트 후 테스트 계정 데이터 삭제, 인기 랭킹에서 테스트 레시피 제거 |
| 장애 발생 방법 | 서버 장애는 VM 강제 종료(전원 끄기), 구성 요소 장애는 해당 컨테이너·서비스 중지 |
| 테스트 전·후 | 시작 전 VM 스냅샷 생성·서비스 정상 확인 (Grafana 대시보드 전체 정상), 테스트마다 `[장애 복구]` 알림·대시보드 정상 확인 후 다음 테스트 진행 |

**비고**

1. Gemini mock: 실제 호출 시 사용량 한도 초과·비용 발생 (05 > 4. 로컬 실행 방식과 동일 이유), mock 응답 지연은 실제와 비슷하게 설정
2. 모니터링 서버 중지 테스트는 blackbox도 함께 멈추므로 관리자 PC의 k6 결과로 측정
3. 스냅샷은 테스트 중 서버가 망가졌을 때만 사용 (DB 서버를 스냅샷으로 되돌리면 그 이후 데이터 유실)

### 3. 부하 테스트

| 시나리오 | 내용 | 목표 |
|---|---|---|
| 일반 API | 로그인, 내 재료 조회·추가, 레시피 상세, 인기 랭킹 조회 | p95 500ms 이내 |
| 추천 (캐시 적중) | 같은 재료 조합으로 반복 추천 요청 | p95 200ms 이내 |
| 추천 (캐시 없음) | 매번 다른 재료 조합으로 추천 요청 (Gemini mock) | 오류 없이 처리, 응답 시간 기록 (외부 API 영향이라 목표 없음) |

| 구분 | 설정 |
|---|---|
| 부하 방식 | 1분 동안 0 → 50명으로 증가, 50명 5분 유지, 1분 동안 감소 |
| 단계별 비교 | 1단계(HTTP, WAS 1대) 기준값 측정 → 2단계(HTTPS) → 3단계(WAS 2대) 같은 조건으로 비교 |
| 함께 확인 | WAS CPU·메모리, DB 연결 수, Redis 캐시 적중률, 에러율 (Grafana) |
| 스크립트 | `load-test/` 폴더, 목표값을 k6 판정 기준(thresholds)으로 넣어 통과 여부 자동 표시 |

※ 목표 미달 시 원인(느린 쿼리, 커넥션 풀, JVM 메모리 등)을 찾아 조정 후 재측정, 조정 내용 기록

### 4. 장애 테스트

| 대상 | 방법 | 1단계 (한계 확인) | 3단계 (목표) |
|---|---|---|---|
| **서버** |  |  |  |
| LB | LB1 강제 종료 | 서비스 중단, 중단 시간 기록 | VIP가 LB2로 이동, 중단 5초 이내 |
| LB 복귀 | LB1 다시 시작 | 서비스 회복 확인 | VIP가 LB1로 돌아옴, 복귀 순간 중단 시간 기록 |
| LB Nginx | LB1의 Nginx만 중지 | - | keepalived가 Nginx 이상 감지 후 VIP 이동, 중단 5초 이내 |
| WAS | WAS1 강제 종료 | API 중단 (화면은 표시), 중단 시간 기록 | WAS2가 처리, 중단 10초 이내 |
| WAS 복귀 | WAS1 다시 시작 | 서비스 회복 확인 | 제외 시간(10초) 후 WAS1에 다시 분배 |
| DB | DB1 강제 종료 | API 중단, 중단 시간 기록 | DB2로 전환, 쓰기 계속, 중단 30초 이내 |
| DB 복귀 | DB1 다시 시작 | DB 정상화 후 서비스 회복 확인 | DB1 자동 재합류(차이만 복제) 후 HAProxy가 DB1로 복귀, 데이터 일치 확인 |
| **구성 요소** |  |  |  |
| Redis | Redis 컨테이너 중지 | 서비스 유지: 추천은 캐시 없이 Gemini 호출, 요청 제한 미적용, 인기 랭킹 숨김, WAS 헬스체크 정상 유지. 재시작 후 캐시·랭킹 유지 (AOF) |  |
| 모니터링 서버 | 강제 종료 | 서비스 유지 (Redis 중지와 같은 영향), 배포 중단, 10분 이내 생존 신호 끊김 알림 수신 | 서비스 유지, garbd 중단에도 DB 2대로 과반 유지 |
| Gemini API | WAS에서 Gemini 주소로 나가는 연결 차단 | 30초 후 안내 메시지 표시, 추천 횟수 차감 안 함, 캐시된 추천은 정상 응답 |  |

**비고**

1. 테스트마다 기록: 장애 시작 시각, 중단 시간, k6 실패 건수, 알림 종류·수신 시각, Grafana 화면
2. 3단계는 장애 3종(LB·WAS·DB)을 포함해 24시간 가용성 99.5% 이상 확인 (00 완료 기준)
3. 모니터링 서버 중지 중에는 다른 장애 알림이 오지 않고, 외부 생존 신호 끊김 알림만 수신 (단일 구성의 한계)
4. 1단계 중단 시간은 3단계 이중화 효과를 보여주는 비교 기준값

### 5. 배포 테스트

| 시나리오 | 확인 내용 | 적용 |
|---|---|---|
| 정상 배포 | 배포 중 API 중단 시간 기록 (중단 허용) | 1단계 |
| 롤링 배포 | 배포 중 k6 초당 10요청, 5xx 에러 0건 | 3단계 |
| 프론트 배포 | 연결 경로 교체 중 화면 오류 없음 | 1단계 |
| 배포 실패 | 헬스체크가 실패하도록 만든 테스트 커밋 배포 → 이전 이미지로 자동 되돌림, `[배포 실패]` 알림 | 1단계 |
| WAS2 실패 | WAS2의 환경 변수 파일 값을 임시로 잘못 넣어 시작 실패 유도 후 배포 → WAS1도 이전 버전으로 되돌림, 두 대 버전 일치 | 3단계 |
| 수동 되돌리기 | `rollback.yml`로 이전 버전 지정 → 백엔드·프론트 해당 버전으로 변경 | 1단계 |

### 6. 백업·복구·재구축 테스트

| 구분 | 방법 | 확인 내용 | 적용 |
|---|---|---|---|
| DB 복구 | 최근 백업 파일을 모니터링 서버의 임시 MariaDB 컨테이너에 복구 (04 > 9. 백업·복구) | 테이블별 데이터 건수 비교, 복구 소요 시간 기록 (NFR-08) | 1단계 |
| 재구축 (1단계) | 초기화한 VM 4대에 playbook 실행 | 수동 작업 없이 서비스 정상 동작 | 1단계 |
| 재구축 (3단계) | 초기화한 VM 7대에 playbook 실행 | 수동 작업 없이 서비스 정상 동작, 이중화 정상 | 3단계 |

※ 재구축 후 DB 데이터는 백업 파일로 복구 (재구축 + 복구 전체 소요 시간 기록)

### 7. 알림·HTTPS 테스트

| 알림 | 방법 | 목표 | 적용 |
|---|---|---|---|
| 서버 다운 | 장애 테스트 중 함께 확인 | 장애 발생 후 3분 이내 Slack 수신, 복구 시 `[장애 복구]` 수신 | 1단계 |
| 백업 실패 | 백업 대상 경로 권한을 임시로 막아 실패 유도 | `[경고]` 수신 | 1단계 |
| 인증서 만료 임박 | 알림 기준일을 임시로 조정 | 14일 전 `[경고]`, 3일 전 `[서버 장애]` 수신 | 2단계 |
| HTTPS 접속 | 브라우저·curl로 443·80 접속 | 유효한 인증서로 응답, 80은 443으로 리다이렉트 | 2단계 |
| 인증서 갱신 | `certbot renew --dry-run` (실제 발급 없이 갱신 과정만 점검) | 성공, 갱신 후 Nginx 재적용 동작 | 2단계 |
| LB2 인증서 | 동기화 playbook 실행 후 LB2로 직접 HTTPS 접속 | LB1과 같은 인증서(만료일 동일) | 3단계 |
| 모니터링 서버 응답 없음 | 모니터링 서버 중지 테스트 중 함께 확인 | 10분 이내 healthchecks.io 알림 Slack 수신 | 1단계 |
| 이중화 전환 | 장애 테스트 중 함께 확인 | LB·DB 전환 발생 `[경고]` 수신 | 3단계 |

### 8. 결과 기록·완료 기준

1. 테스트별 결과를 `docs/09-test.md`에 표로 기록 (목표, 측정값, 통과 여부, Grafana 화면)
2. 1단계와 3단계 장애 중단 시간 비교표 작성
3. 00 기획 > 완료 기준의 단계별 목표 전체 통과
4. 미달 항목은 원인·조치·재측정 결과 기록
