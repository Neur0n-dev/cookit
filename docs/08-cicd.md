# 08. CI/CD

### 1. 전체 흐름

1. 작업 브랜치에서 PR 생성 → CI(테스트·빌드) 자동 실행, 실패 시 병합 차단
2. PR을 `main`에 병합 → 바뀐 경로(`backend/`, `frontend/`)에 해당하는 배포만 자동 실행, 둘 다 바뀌면 백엔드 → 프론트 순서
3. 빌드는 GitHub 서버, 배포는 모니터링 서버의 Self-hosted Runner가 내부 서버에 실행
4. 배포·되돌리기 결과(성공·실패, 커밋 해시)를 Slack으로 알림 (장애 알림과 같은 채널, 메시지 앞 `[배포 성공]`·`[배포 실패]`·`[되돌리기 완료]`·`[되돌리기 실패]`로 구분)

### 2. 워크플로 구성

| 파일 | 실행 시점 | 실행 위치 | 작업 |
|---|---|---|---|
| ci.yml | PR 생성·수정 | GitHub 서버 | 백엔드: 테스트(Testcontainers 포함)·빌드 / 프론트: 타입 검사·빌드. 모든 PR에서 실행하고 바뀐 경로의 작업만 수행 (나머지는 건너뜀 → 통과 처리) |
| deploy.yml | `main` 병합 | 빌드: GitHub 서버<br>배포: Runner | 바뀐 경로 확인 → 백엔드 배포(이미지 빌드·GHCR 저장·WAS 교체) → 프론트 배포(빌드·LB 업로드·경로 교체). 바뀐 쪽만 실행 |
| rollback.yml | 수동 실행 (커밋 해시 입력) | Runner | 지정한 버전으로 백엔드 또는 프론트 되돌리기 (최근 5개 버전 이내) |

**비고**

1. 배포 작업은 Ansible playbook으로 실행 (워크플로는 playbook 호출만 담당)
2. 배포 순서는 백엔드 → 프론트 고정, 백엔드 실패 시 프론트 배포 안 함 (새 화면이 없는 API를 호출하는 것 방지)
3. API는 하위 호환 유지 (이전 API 바로 삭제 금지), 삭제가 필요하면 프론트에서 먼저 사용 중단 후 다음 배포에서 백엔드 삭제
4. 배포는 한 번에 하나만 실행 (동시 실행 방지 설정), 진행 중 새 배포는 대기
5. CI는 문서만 바뀐 PR에서도 실행 (CI 통과 필수 설정 때문에, CI가 실행되지 않으면 병합 불가)
6. 되돌리기는 보관 중인 최근 5개 버전(이미지·프론트 폴더) 이내에서만 가능, DB는 되돌리지 않음 (컬럼 추가 위주 변경이라 이전 앱도 동작, Flyway는 앱보다 새로운 DB 버전 허용)
7. `infra/` 변경은 자동 적용하지 않음 → 관리자가 모니터링 서버에서 미리보기(`--check`) 후 직접 실행
8. 브랜치 보호 규칙의 CI 통과 필수 항목은 `ci.yml` 첫 실행 후 등록 (05 > 5. 브랜치·커밋 규칙)

### 3. 백엔드 배포 절차

| 순서 | 작업 | 적용 |
|---|---|---|
| 1 | GitHub 서버에서 이미지 빌드, GHCR에 커밋 해시 태그로 저장 | 1단계 |
| 2 | Runner가 WAS에 새 이미지 내려받기, 비밀 정보는 WAS의 환경 변수 파일(권한 600)로 전달 | 1단계 |
| 3 | 현재 컨테이너 종료(처리 중 요청 완료 후, 종료 대기 최대 40초) → 새 컨테이너 시작 (교체 중 API 잠시 중단 허용) | 1·2단계 |
| 4 | 헬스체크(`/actuator/health`) 최대 90초 대기, 정상이면 완료 | 1단계 |
| 5 | 실패 시 이전 이미지로 자동 되돌림, 실패 알림 | 1단계 |
| - | 롤링: WAS1 교체 → 헬스체크 정상 → WAS2 교체. WAS1 실패 시 WAS2는 진행 안 함, WAS2 실패 시 WAS1도 이전 버전으로 되돌림 (WAS 간 버전 불일치 방지) | 3단계 |

**비고**

1. 헬스체크 대기 90초: 앱 시작 + DB 변경(Flyway) 적용 시간 고려
2. WAS마다 현재·이전 이미지 태그를 기록해 되돌릴 대상 확인
3. 3단계 무중단 조건: graceful shutdown(앱) + 연결 실패 시 다른 WAS로 재시도(Nginx)

### 4. 프론트 배포 절차

| 순서 | 작업 | 적용 |
|---|---|---|
| 1 | GitHub 서버에서 React 빌드, 빌드 파일을 워크플로 결과물(artifact)로 저장 → Runner가 내려받기 | 1단계 |
| 2 | Runner가 LB에 새 폴더(`releases/커밋해시/`)로 업로드 | 1단계 |
| 3 | 연결 경로(`current`)를 새 폴더로 교체 (교체 순간 중단 없음) | 1단계 |
| 4 | 최근 5개 버전만 남기고 이전 폴더 삭제 | 1단계 |
| - | LB1·LB2 모두 업로드 성공 시에만 두 대의 연결 경로 교체, 하나라도 실패하면 둘 다 교체 안 함 (LB 간 버전 불일치 방지) | 3단계 |

**비고**

1. 프론트 배포 실패 시 연결 경로를 바꾸지 않아 이전 화면 유지, 백엔드는 되돌리지 않음 (API 하위 호환으로 이전 화면도 정상 동작)
2. 실패 알림 후 원인 수정 → 다시 배포 (실패한 워크플로 재실행 가능)
3. 되돌리기는 연결 경로를 이전 폴더로 바꾸기만 하면 즉시 반영

### 5. 비밀 정보·이미지 관리

| 구분 | 설정 |
|---|---|
| GitHub Secrets | DB 앱 계정 비밀번호, Redis 비밀번호, JWT 키, Gemini API 키, Slack Webhook URL(배포 알림) |
| 보호 설정 | Secrets는 배포 환경(`production`)에만 등록, `main` 브랜치 배포에서만 사용 가능 |
| 이미지 공개 | GHCR 이미지 공개 (비밀 정보는 이미지에 넣지 않고 실행 시 주입) → WAS는 로그인 없이 이미지 내려받기 |
| 이미지 정리 | 최근 5개 버전만 보관(프론트와 동일), 이전 이미지는 자동 삭제 |
| 배포 SSH 키 | Runner 계정 홈 폴더에 보관 (권한 600), GitHub Secrets에는 등록하지 않음 (GitHub 밖으로 나갈 일이 없음) |

※ Redis 비밀번호·Slack Webhook URL은 서버 구성(Ansible Vault)에도 쓰이므로 같은 값을 양쪽에 등록 (Runner는 Vault에 접근하지 않음, 6. Runner 보안 참고)

### 6. Runner 보안

| 구분 | 설정 | 이유 |
|---|---|---|
| 실행 대상 | Runner는 `main` 배포 작업만 실행, PR의 CI는 GitHub 서버에서만 실행, 외부 기여자 PR은 승인 후 실행 | 공개 저장소는 누구나 PR을 올릴 수 있어, 외부 코드가 내부 서버에서 실행되는 것 차단 |
| Runner 등록 | 이 저장소 전용, 라벨(`cookit-deploy`) 지정 작업만 실행, 서비스로 등록(재시작 시 자동 실행). Runner가 GitHub에 443으로 먼저 접속하는 방식이라 들어오는 포트 없음 | 다른 작업 실행 방지, 방화벽 인바운드(외부 → 내부) 포트 불필요 |
| 실행 계정 | Runner 전용 계정 (관리자 권한(sudo) 없음, Ansible 실행 계정과 분리), Vault 비밀번호 파일 접근 불가 | Runner가 뚫려도 서버 비밀 정보 보호, 배포에 필요한 값은 GitHub Secrets에서 받음 |
| 배포 대상 계정 | WAS·LB에 배포 전용 계정(`deploy`)과 전용 SSH 키 사용 (WAS는 Docker 실행, LB는 화면 폴더 쓰기 권한만) | 배포에 필요한 작업만 가능하도록 권한 제한 |
| 워크플로 작성 규칙 | 자동 발급 토큰(`GITHUB_TOKEN`)은 기본 읽기만, 이미지 저장 작업에만 쓰기 권한. 외부 액션은 버전 고정 (예: `actions/checkout@v4`) | 토큰 노출·액션 변조 시 피해 최소화 |

### 7. 완료 기준

1. PR 생성 시 CI 자동 실행, 실패 시 병합 차단 확인
2. `main` 병합 후 백엔드·프론트 자동 배포, Slack 결과 알림 수신
3. 헬스체크 실패 상황을 만들어 자동 되돌림 확인, 수동 되돌리기(`rollback.yml`) 확인
4. 3단계 롤링 배포 중 서비스 무중단 확인 (09 테스트에서 측정)
